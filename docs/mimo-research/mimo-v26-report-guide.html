리포트 3장

사전학습과 중간학습: RL을 위한 몸 만들기

사전학습은 넓은 지식을, 중간학습은 "RL에서 탐색할 수 있는 능력"을 만듭니다. 이 리포트에서 중간학습은 RL 준비 단계로서 비중이 큽니다.

사전학습: 텍스트 먼저, 그다음 옴니

1단계는 언어 백본을 텍스트로만, 2단계는 ViT와 오디오 인코더를 붙여 이미지·영상·오디오까지 함께 학습합니다. 문맥은 32K로 시작해 도중에 256K로 늘립니다. 옵티마이저는 AdamW입니다.

작은 Flash가 오히려 더 많은 토큰(48T)을, 특히 옴니 데이터를 훨씬 많이 봤습니다.

중간학습: 세 가지를 바꾼다

데이터를 에이전트 쪽으로

코딩·범용·시각·리서치 에이전트 궤적에 레포 단위 코드와 멀티모달 데이터를 섞습니다. 대부분의 연산은 256K에서 쓰고, 마지막에 1M으로 늘립니다.

AdamW → Muown

혼합 과제 RL에서 배치를 키울수록 AdamW의 효율이 떨어졌습니다. 행렬 단위로 업데이트를 직교화하는 Muon은 큰 배치에서도 데이터 효율이 유지됩니다. 행 노름을 제어하는 변형(Muown)을 hidden 행렬에 쓰고, 임베딩·LM head·router는 AdamW로 둡니다. 전환 중 loss spike는 없었습니다.

MXFP4 QAT

RL 롤아웃을 MXFP4 expert로 돌리기 위해 저정밀 연산에 미리 적응시킵니다.

reward hacking 대응개발 초기 RL 실험에서 공개된 수정을 베끼는 hack이 보이자, 중간학습 단계로 되돌아가 그 궤적을 "실수를 알아차리고 고쳐 가는" 형태로 다시 쓴 데이터를 넣었습니다. 그 뒤 SFT와 최종 RL(30스텝, 한 번)을 다시 진행했습니다. 어느 체크포인트에서 중간학습을 다시 시작했는지는 리포트에 없습니다.

리포트가 말하지 않은 것들

추정"짧은 SFT"는 무엇을 했나

본 모델의 SFT는 "Following a short supervised fine-tuning (SFT) stage" 한 문장이 전부입니다. 데이터, 양, 스텝 수가 없습니다. 에이전트 능력은 중간학습에서 이미 만들었으니, SFT는 RL을 시작할 수 있는 상태로 맞추는 단계였을 것입니다.

  • 형식: 대화 템플릿, 사고 과정, 도구 호출 형식. 깨지면 롤아웃이 첫 턴에서 망가져 보상이 전부 0입니다.
  • 하니스 적응: mini-harness별 시스템 프롬프트와 도구 스키마
  • 출발 통과율: 대시보드 첫 스텝에서 전부 실패 14.6%, 전부 성공 17.8%. 약 2/3의 프롬프트가 학습에 쓰일 수 있는 상태로 출발했습니다.
  • 범용 기본선: 같은 SFT 모델이 루브릭 채점기로도 쓰였습니다.

"짧게" 한 이유는, SFT를 오래 하면 출력 분포가 좁아져 RL이 다양한 시도를 샘플링하기 어려워지기 때문으로 보입니다.

추정중간학습의 loss와 마스킹

loss도 리포트에 없습니다. 보상이나 롤아웃 이야기가 없고 데이터가 사전학습식 혼합이니 RL이 아닌 NTP이고, 백본의 MTP 모듈이 사전학습용이라 NTP + MTP 보조 loss를 유지했을 것입니다.

도구 출력(파일 내용, 테스트 로그)은 마스킹 없이 학습했을 가능성이 높습니다. "loss 토큰"을 따로 보고하는 건 9B 증류 SFT뿐이고(77.4B 중 27.2B), 사전·중간학습은 전체 토큰 수만 말합니다. 도구 출력은 대부분 레포 코드라 그 자체로 좋은 데이터이고, 환경 반응을 예측하는 학습은 RL에서 행동을 고르는 바탕이 됩니다.

생각 부분만 학습했을 가능성은 낮습니다. 에이전트 능력의 핵심은 도구 호출과 편집 같은 행동이고, 교정 데이터도 "continues with actions"까지 보여줍니다.

추정그러려면 과제 단위 분리가 필요하다

중간학습에서 어떤 과제의 궤적을 봤다면 모델은 그 과제의 환경 정보(숨은 테스트, 파일 구조)와 정답을 이미 압니다. 도구 출력을 마스킹해도 정답은 모델 자신의 턴에 남아 막을 수 없습니다. 해법은 중간학습용, RL용, 평가용 과제를 처음부터 겹치지 않게 나누는 것이고, 그러면 마스킹할 이유도 사라집니다.

원리는 이렇습니다. 원하는 것은 처음 보는 과제의 성공률 인데, RL은 유한한 과제 집합의 평균 을 최적화합니다. 이게 의 대리가 되려면 가 초기 정책과 독립이어야 합니다. 중간학습에서 본 과제는 이 독립성을 깨서, 보상과 상관된 행동이 "풀어내기"가 아니라 "떠올리기"가 됩니다. 떠올리는 능력은 처음 보는 과제로 옮겨가지 않습니다.

  • Partial rollout: 배치가 차면 진행 중인 궤적을 멈췄다가 다음 단계에서 이어서 생성. 대가는 정책이 바뀔 때마다 KV를 다시 채우는 re-prefill이고, 큰 배치가 이 비용을 나눠 냅니다.
  • 학습-추론 일치: routing replay(R3)와 top-p 후보 집합 replay
  • Dynamic sampler: 전부 통과·전부 실패 그룹을 걸러 모든 샘플이 gradient를 갖게 함
  • Sample Mixer: 롤아웃 시간이 제각각인 과제들 사이에서 배치 구성을 목표대로 유지

"배치가 찼다"는 것

학습에 쓸 수락된 그룹이 데이터 소스마다 목표 수만큼 모인 순간입니다(리포트 6.2절의 batch yield). 롤아웃이 모두 끝났다는 뜻이 아닙니다. 수락률이 1보다 낮으니 목표보다 훨씬 많이 생성하고, 그 순간에도 긴 롤아웃 상당수가 생성 중입니다.

  1. 모든 소스가 스케줄링 가중치대로 생성합니다. 할당량을 채운 소스도 멈추지 않고(목표 항), 못 채운 소스가 우선권을 받습니다(부족분 항).
  2. 모든 소스가 할당량을 채우면 진행 중인 궤적을 소스와 관계없이 전부 멈춥니다.
  3. 학습하고 가중치를 갱신합니다.
  4. 멈췄던 궤적을 새 정책으로 이어서 생성합니다(KV re-prefill). 초과로 수락된 그룹은 다음 스텝으로 이월됩니다.
추정"fully asynchronous"의 실제 의미: colocate + partial rollout

보통 비동기 RL은 생성과 학습이 따로 동시에 도는 구조를 말합니다. 이 런은 그렇지 않고, 같은 자원에서 생성과 학습을 번갈아 돌린 것으로 보입니다.

  • 4.1절: 진행 중인 궤적을 멈췄다가 "resume them in the next rollout phase". 단계가 나뉘어 있다는 뜻입니다.
  • 6.3절: 롤아웃 시간을 "excluding pauses between training steps"로 정의합니다.
  • 그림 16: 스케줄링 시뮬레이션에서 학습 시간을 뺍니다.
  • 6.4절: optimizer 상태를 CPU에 두고 업데이트 때만 복사합니다. 같은 GPU에서 생성할 때 HBM을 비우는 colocate 기법입니다.
  • 공개 대시보드: 스텝 시간이 생성 시간과 학습 시간의 합과 98% 일치합니다(pro 중앙값 0.979). 대시보드의 생성 시간이 "트레이너가 기다린 시간"이라면 비동기에서도 성립하는 식이라 단독 근거로는 약합니다.

리포트가 비동기라 부를 만한 건 세 가지입니다. 한 궤적이 여러 정책 버전(최대 4)에 걸치는 것, 그룹이 따로따로 끝나는 것, grader가 생성과 나란히 도는 것. 흔히 말하는 semi-async에 가깝습니다.

리포트 4.2절

RL 축 ②: 환경과 하니스를 넓힌다

좋은 RL 환경의 조건은 셋입니다. 실제 과제를 닮을 것, 대규모로 재현 가능할 것, 보상이 과제 목표와 맞을 것. 리포트는 특히 세 번째, 감독의 질에 공을 들입니다.

코드 에이전트

다섯 갈래로 과제를 만들고 두 번 검증

  • 합성: GitHub PR·이슈, 사내 개발 요청(vibe coding 포함), 상세 명세 구현, 기존 코드에서 기능 역추출(CodeMidas), 장기 엔지니어링 과제 + 공개·구매 데이터
  • 정확성: 과제마다 에이전트가 4번 풀고, 감사 에이전트가 명세 기준으로 판단해 보상과 어긋나는 거짓 양성·거짓 음성을 찾음
  • 안정성: 참조 패치 전후 F2P·P2P 테스트 결과가 8번 재실행에서 일관돼야 통과
범용 에이전트

로컬 모의 소프트웨어 위의 실무

  • 실제 파일을 모으고, 멀티에이전트가 소프트웨어 mock을 만들어 모든 상태를 로컬에 두고 초기화 가능하게 함
  • 채점은 원자적 이진 루브릭: 코드 검사(DB 값, 형식) + LLM 검사(열린 내용)
  • 여러 능력대 모델의 롤아웃을 검토해 너무 엄격하거나 느슨한 항목을 고치고, 관계없는 파일 변경을 잡는 부정 검사 추가
  • RL 중 채점은 자체 호스팅한 MiMo-V2.6-SFT
시각 에이전트

디자인과 복제, 두 종류

  • 열린 디자인: 동작·지시 준수·레이아웃·기본 미감을 개별 루브릭으로 다진 뒤, 같은 질의의 결과물을 그룹으로 비교해 강약을 가림
  • 고정밀 복제: 픽셀 유사도 같은 규칙 지표 + LLM 종합 판정
사이버보안

"그 버그"를 정확히 재현했는가

  • OSS-Fuzz의 수만 건 확인된 취약점. 에이전트가 특정 버그를 터뜨리는 입력을 만듦
  • 판정: sanitizer 보고서의 취약점 종류와 최상위 프로젝트 스택 프레임이 둘 다 문자열로 일치해야 통과. 결정적이고 싸며 LLM 판정의 흔들림이 없음
  • CyberGym과 달리 컴파일된 하니스 바이너리를 주어 디버거 기반 분석을 허용

Multi-harness: 한 하니스에 길들지 않게

Codex 같은 실제 제품 하니스는 보상과 무관한 안전장치와 지시문이 많아 credit assignment가 흐려지고, 모듈이 엮여 있어 하나만 바꿔 실험할 수 없습니다. 그래서 시스템 프롬프트·도구·문맥 관리만 있는 최소 agent loop에서 출발해, 과제별로 조합을 바꾼 mini-harness들을 만들었습니다. 효과는 30스텝 런에서 확인됩니다. 학습에 안 쓴 codex, claude code, mini-swe-agent의 DeepSWE 평균이 약 50%에서 66%로 올랐고, 학습 하니스와의 격차도 줄었습니다.

Reward hacking: 학습 밖에서 먼저 막는다

레포 수리 과제에서 가장 흔한 편법은 정답 유출입니다. 버그 리포트에서 수정을 끌어내는 대신, 이미 공개된 수정을 어딘가에서 가져옵니다. 리포트 표 2의 실제 사례입니다.

  1. 환경 정리: 빌드 로그, 검증기 출력, 남은 패치, 바이트코드, 캐시 제거. git 이력은 기준 커밋까지만. 컨테이너 네트워크 격리.
  2. Hack agent: 전담 에이전트가 남은 유출 경로를 찾게 하고, 찾으면 정리 후 다시 돌림. 어떤 환경에서도 exploit를 못 찾을 때까지 반복.
  3. 학습 중 감사: 궤적을 정기적으로 오프라인 감사. 학습 안에서는 GAR grader가 확정 hack의 reward를 0으로.

그 결과 확정 hack 비중은 두 모델 모두 학습 내내 2% 미만이었습니다.

추정여기 나오는 "에이전트"는 어떤 모델인가

리포트가 모델을 밝힌 건 셋뿐입니다. 범용 과제의 RL 중 채점기는 자체 호스팅한 MiMo-V2.6-SFT, GAR 채점기는 "SFT-trained agentic grader", hack 교정 데이터는 "MiMo"가 고쳐 썼습니다. 과제를 4번 푸는 coding agent, 감사·계획·검토 agent, hack agent, 이슈를 재구성하는 LLM은 모델이 나오지 않습니다.

  • 환경 구축 에이전트는 RL 전에 일합니다. 그 시점에 있던 모델(이전 세대 MiMo, V2.6 SFT 체크포인트, 외부 모델)을 썼을 것이고, 학습 중인 정책은 필요 없습니다.
  • RL 중 채점기는 고정된 SFT 스냅샷입니다. 학습 중인 정책을 채점기로 쓰면 채점 기준이 매 스텝 바뀌고, 정책이 자기 채점기를 속이는 쪽으로 함께 움직일 수 있습니다.
추정hack이 나온 환경과 과제는 어떻게 되나

환경은 버리지 않고 고쳐서 다시 씁니다(리포트: 발견한 경로로 정리를 보강하고 hack agent를 다시 돌림). 교정되는 건 궤적 쪽이고, 중간학습 데이터로 들어갑니다. 학습 도중 소스를 통째로 뺀 사례도 있습니다(대시보드 공지: pro 15스텝에 cyber 제외).

걸리는 점은, 교정 궤적이 "과제 명세에 근거해 행동을 이어간다"로 끝나면 그 과제의 정상 풀이가 중간학습에 들어갈 수 있다는 것입니다. 원리적으로는 사례로 쓴 과제를 RL과 평가 풀에서 빼는 것이 맞습니다(리포트 3장 부분의 "과제 단위 분리" 참고). 리포트는 이 처리를 말하지 않습니다.

리포트 4.3절

RL 축 ③: 채점에 연산을 쓴다

테스트 통과는 "맞았다"만 알려주고 "잘 풀었다"는 알려주지 않습니다. 통과한 해답들 사이의 품질 차이를 신호로 바꾸는 두 방법이 이 리포트의 핵심 기여입니다.

GRS · 통과율 높은 일부 과제

오프라인으로 만든 과제별 루브릭

에이전트가 오프라인 롤아웃 여러 개를 비교해 해결책 루브릭(요구 충족, 엣지 케이스, 코드베이스와의 일관성)과 행동 루브릭(증거 수집, 변경 효과 확인)을 만듭니다. 학습 중 grader가 각 롤아웃을 채점해 테스트 보상에 곱합니다.

실패는 여전히 0. 전부 통과한 그룹에서도 품질 차이가 남습니다.

GAR · 나머지 코드 과제

온라인으로 그룹을 비교해 credit 재배분

SFT로 학습한 grader가 한 작업 공간에서 그룹 전체(패치, 테스트 출력)를 보고, 통과한 패치를 다섯 기준으로 순위 매깁니다: 접근의 적절성, 구현의 정확성, 최소성, 부작용 회피, 코드베이스 관례. 코드를 직접 읽고 테스트를 돌려볼 수 있고, 유출된 답에 의존했으면 reward를 0으로 바꿉니다.

GAR의 재배분은 통과 롤아웃의 양수 advantage를 품질 factor 로 줄인 뒤, 줄어든 양을 공통 배율 로 통과 롤아웃들에 되돌립니다. 그래서 좋은 통과는 원래보다 커지고 나쁜 통과는 작아지며 양수 총량은 그대로입니다. 에는 상한이 있고, 그 뒤 그룹 평균을 빼 합을 0으로 맞춥니다.

왜 이렇게 하나양수만 깎고 끝내면 음수 쪽이 상대적으로 커져 엔트로피가 폭주합니다. 재정규화는 그 균형을 되돌리는 안전장치입니다. flash로 코드만 학습한 비교에서, GAR이 없으면 턴 수와 길이가 빠르게 늘어 길이 한도에 걸리고 통과율 상승이 멈췄습니다. GAR을 쓰면 52스텝까지 통과율이 계속 오르고 턴 수는 거의 일정했습니다. 코드 감사에서도 GAR 없는 정책은 예외 삼키기, 검증 완화, 평가용 설정 변경 같은 "통과용 우회"를 늘렸습니다.

행동 정규화: 길이와 형식 오류

그룹 상대 길이 페널티

통과율이 문턱 를 넘는 그룹에서만, 성공한 롤아웃 길이의 분위수를 기준으로 너무 긴 성공을 최대 만큼 깎습니다. 어려운 프롬프트는 탐색 여지를 남깁니다.

세그먼트 단위 행동 페널티

깨진 markup, 없는 도구 이름, 잘못된 인자를 낸 토큰을 표시합니다. 성공 궤적에서는 그 토큰의 advantage를 0으로, 실패 궤적에서는 배로 키웁니다. 뺀 양수는 표시 안 된 양수 토큰에, 더한 음수는 표시 안 된 음수 토큰을 덜 벌하는 데 돌려 부호별 총량을 보존합니다.

와 GAR의 factor·상한 값은 리포트에 나오지 않습니다. 공개 학습 대시보드 로그로 역산한 값(factor 1 / 0.625 / 0.2, 상한 1.5 등)은 별도 역산 페이지에 정리했습니다.

리포트 5.1~5.5절

실험: 단 한 번의 30스텝 RL

5장의 부제는 "You Only RL Once"입니다. 여러 번 돌려 고르는 대신 한 번의 계획된 런을 끝까지 운영했고, 학습 로그를 실시간으로 공개했습니다.

학습 설정

과제 비중에이전트·경쟁 코딩 68%, 미적 디자인 13%, 범용 도구 사용 12%, 사이버보안 4%, 문맥 따르기 3%
알고리즘GRPO, partial rollout (staleness 4). 리포트 표현은 "fully asynchronous"이지만 생성과 학습은 번갈아 돈 것으로 보임 (리포트 4.1절 부분 참고)
옵티마이저Muown, lr 3e-6, warmup·weight decay 없음, grad clip 1.0, Nesterov momentum 0.95, Newton–Schulz 10회. Adam 부분은 β₁ = β₂ = 0.95
loss 집계프롬프트 단위 평균. 토큰 전체 평균보다 응답 길이 증가가 느림
중요도 비율토큰별 학습/롤아웃 확률비. 양수·음수 advantage에 따로 경계를 두고(초기 [0.2, 5.0]) 엔트로피가 낮으면 양수 경계를 넓히고 음수 경계를 좁힘
기타SFT의 FP32 master weight와 Muown 상태를 이어받아 MXFP4 학습 안정화. router 고정

Router를 얼린 이유

router를 학습 가능하게 두고 Pro를 돌리면 20스텝 만에 layer 9의 expert 부하가 무너졌습니다. step 20 checkpoint에서 router만 RL 전 값으로 되돌리면 부하는 회복되고 벤치마크는 그대로였으므로, 원인은 expert 가중치가 아니라 router 표류였습니다.

부하 변동계수 (std / mean)0.78 → 2.0≈ 0.7
최대 부하 (max / mean)6× → 16×≈ 5.5×
차가운 expert (평균의 0.1배 미만)0.5% → 22%≈ 1%

무엇이 멈춰 세웠나

30스텝에 Pro는 123.1시간Flash는 81.8시간이 걸렸습니다. 중단 원인은 네 종류입니다.

  • 인프라

    주로 GPU 메모리 double-bit error. Pro는 step 14 뒤 grader가 네트워크에서 끊겨, Flash는 step 15~16 사이 Kubernetes 장애로 cyber 클러스터 pod가 죽어 재시작

  • 추론

    재시작 직후 짧은 롤아웃이 먼저 끝나 길이 추정이 치우치고 KV 풀이 고갈. 한 하니스가 같은 데이터셋에서 다른 하니스의 절반도 안 되는 길이를 내 추정을 흔듦

  • 학습

    GPU OOM. 전체 배치는 고른데 micro-batch 하나에서 EP rank 하나가 평균의 30배 토큰을 받음. 병렬화를 바꿔 activation 메모리를 줄임

  • 드라이버

    Flash 후반, 길어진 시퀀스를 packing하다 노드의 CPU 메모리가 넘침

얻은 것

두 모델 모두 DeepSWE v1.1, AutomationBench v1.0.6, MiMo Visual Coding에서 체크포인트 간 요동은 있지만 전반적으로 올랐고, 총 토큰 사용량도 함께 늘었습니다. 리포트는 "성능 향상이 토큰 사용 증가와 함께 왔다"고 정리합니다.

리포트 5.6절

MOPD2: 검증하기 어려운 능력은 증류로 붙인다

RL은 보상을 잴 수 있어야 합니다. 게임 개발, 과학 연구, embodied 과제처럼 채점기를 만들기 어려운 영역은 전문 교사 모델에게 배웁니다.

교사

영역별 전문가

검증 가능한 과제는 혼합 RL로 학습한 교사, 열린 과제는 고품질 합성 시연으로 SFT한 교사.

Standard MOPD

학생이 끝까지 생성

학생이 전체 롤아웃을 만들고 RL 교사가 토큰 단위로 지도합니다(MiMo-V2-Flash 방식).

Prefix-Conditioned OPD

남의 궤적에서 한 턴만

교사 롤아웃이나 SFT 데이터의 궤적에서 턴이 k개면 이력 prefix도 k개. 각 prefix에서 학생이 다음 한 턴만 생성하고 교사가 지도합니다. 긴 과제에서 학생이 초반부터 엇나가 교사가 본 적 없는 상태로 가는 문제를 줄입니다.

SFT 데이터는 "따라 써야 할 답"이 아니라 "문맥"으로만 쓰입니다. 학생은 그 문맥에서 자기 답을 생성하고, 교사가 그 답을 평가합니다. 최종 성능 표(표 3)는 이 단계를 거친 모델의 결과입니다.

리포트 8장

이 리포트를 한 문단으로

MiMo-V2.6은 긴 문맥을 싸게 처리하는 하이브리드 SWA MoE 위에, 에이전트 궤적 중심의 중간학습과 Muon 전환으로 큰 배치 RL을 준비했습니다. 그다음 한 번의 30스텝 혼합 RL에 연산을 세 방향으로 쏟았습니다. 배치와 처리량, 환경과 하니스의 다양성, 그리고 통과한 해답끼리 비교하는 에이전트 채점입니다. 이 채점(GRS, GAR)이 길이 폭주와 "통과용 우회"를 누르면서 성능을 계속 끌어올린 핵심 장치로 제시됩니다. 검증이 어려운 능력은 MOPD2 증류로 붙였고, 같은 레시피를 9B 모델과 환경으로 공개해 재현 가능한 출발점을 남겼습니다.

리포트가 밝히지 않은 것: 길이 페널티와 세그먼트 페널티의 상수, GAR factor와 상한 값, 30스텝으로 정한 이유, IS 경계의 조정 궤적.
